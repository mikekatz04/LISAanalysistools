# Sig-het v5 — design change, implementation, and the GPU checklist

**Date:** 2026-08-04
**Spec:** `specs/2026-08-03-sighet-v5-global-residency-design.md` — **its central
rationale is wrong**; see §1. The spec should be amended or superseded by this
document rather than left standing.
**Status:** implemented; **compiled and bit-identical to v4 on the CPU
backend** (§4.2); **never run on a GPU** (`which nvcc` → not found).
**Nothing committed, nothing pushed.**

---

## 1. Why v5 is not what the spec says it is

The spec's premise:

> The fold blocks are *the reference*: `A0/A1/B0/B1` and the `c0` row are
> identical for every candidate … Today every resident block loads its own
> private copy into its own shared memory … In global memory there is **one
> copy** read by all blocks.

That is not what the v4 kernel does. `c0_sparse_all`, `A0_all`, `A1_all`,
`B0_all`, `B1_all`, `B0nc_all`, `B1nc_all` are **already kernel pointer
arguments read straight from global memory** — the `|c0|` row scan
(`gb_tdi_on_the_fly.cu`, v4 scorer), the `d_h` fold and both `h_h` folds
dereference them directly. They are never staged into shared. There is nothing
to de-duplicate and no L2-sharing win.

What actually occupies v4's shared memory is **per-candidate scratch**:

| array | elements | bytes / sparse-time point (nch=3, M=5) |
|---|---|---|
| `r_pix` | `nch · N_sparse_t` | 48 |
| `r_sparse` | `nch · M · N_sparse_t` | 240 |
| `dr_sparse` | `nch · M · N_sparse_t` | 240 |
| | | **528** |

The spec's *arithmetic* was right — 528 B/point matches this carve to the byte,
and so does its 143.4 KB / 1-block-per-SM conclusion. Only the **identity** of
those bytes, and therefore the proposed remedy, were wrong. The occupancy
argument — the actual point of the experiment — survives intact.

The relocate-to-global implementation written on 2026-08-03 was built on the
wrong premise and has been **replaced**. Relocating per-candidate scratch to
global would have added ~700 KB/candidate of traffic to buy 4 blocks/SM. The
design below buys **5** and removes 95 KB/candidate instead.

## 2. What v5 is now

Two observations, both about `r_sparse`/`dr_sparse`:

**(1) They are redundant.** By v4's own construction

```
r_sparse[c][im][b]  = keep(c, im, b) ? r_pix[c][b] : 0
dr_sparse[c][im][b] = centred difference of that masked row
```

so 480 of the 528 bytes per point are an M-fold replication of `r_pix`
modulated by **one bit** per (row, pixel). v5 keeps `r_pix` and the bit and
rebuilds r/dr in registers at the point of use.

**(2) The mask is candidate-independent.** `keep()` compares `|c0|` against
`1e-12 · max_b |c0|` along the row, and `c0_sparse_all` depends only on
`data_idx` — never on the candidate. v4 nevertheless recomputes the row maxima
and the mask inside *every candidate's block*: two full passes over
`nch·M·N_sparse_t` global `c0` values, on `nch·M = 15` of 128 threads. v5
hoists both into `setup_in_model`, bit-packed along the pixel axis
(`c0_mask_all`, 1/128 the size of `c0`).

**(3) Shared regions are overlaid by lifetime.** The scorer runs in four phases
separated by `__syncthreads()` that already exist, and most of the carve is
dead outside its own phase:

| region | arrays | live in |
|---|---|---|
| A | `params_c`, `params_r` | all |
| B | `t_nodes` | P1, P2 |
| C | `dlnA`, `dphi`, `cA1-3`, `cP1-3` | P1, P2 |
| Bk | `t_knots` | P1, P2 |
| D | `B_b`, `pcr` — **node-sized**: banded mode skips the knot solve, so v4's knot-sized workspace is 4 608 B of pure waste | P1 |
| E | `tdi_c/tdi_r`, `phiun_c/r`, `amp_y`, `ph_y`, `flip`, `pjump`, `count`, `fix_c` | P1 |
| F | `rk_re`, `rk_im` | P2, P3 |
| G | `rpix_re`, `rpix_im`, `mask_sh` | P3, P4 |

P1 node stage → P2 knot resample → P3 banded `r_pix` → P4 fold. So **F aliases
E** and **G aliases B+C+Bk+D**, and the arena is max-over-phases rather than
sum-over-arrays.

`r_pix` is also split into two `double` arrays instead of one `cmplx` array: a
warp reading 32 consecutive `cmplx` resolves in 4 shared-memory phases against
2 for doubles, and both `r_pix` loops already compute `re`/`im` separately, so
the split costs nothing.

**v5 is bit-identical to v4 by construction, not to round-off.** The fold's
index mapping, operands, operation order and block reduction are unchanged; the
node stage, knot resample and banded cardinal application are *spliced verbatim*
out of the v4 scorer at build time rather than retyped.

## 3. The numbers

Banded mode, `n_nodes=64`, `n_knots=128`, `nch=3`, `M=5`, `band_len=16`, 128
threads. Per-block totals include the 2 176 B static staging
(`d_h_tmp`/`h_h_tmp` + cub) and the 1 KB the driver reserves on sm_80+ — both
omitted from the spec's arithmetic and together worth a whole block.

| `N_sparse_t` | v4-banded | A100 blk | v5-flat | blk | **v5** | **A100 blk** | **H100 blk** |
|---|---|---|---|---|---|---|---|
| 127 | 103.7 KB | 1 | 39.8 KB | 3 | **27.6 KB** | **5** | 7 |
| **204** | **143.4 KB** | **1** | 43.7 KB | 3 | **27.6 KB** | **5** | 7 |
| 256 | 170.2 KB | ✗ | 46.1 KB | 3 | 27.6 KB | 5 | 7 |
| 408 | 248.6 KB | ✗ | 53.6 KB | 2 | 27.6 KB | 5 | 7 |
| 510 | 301.2 KB | ✗ | 58.5 KB | 2 | 31.2 KB | 4 | 6 |
| 1078 | 594.0 KB | ✗ | 86.2 KB | 1 | 58.8 KB | 2 | 3 |

✗ = exceeds the 163 KB **per-block** limit: that grid is *unreachable* under
v4, not merely slow. v5's footprint is constant in `N_sparse_t` up to N ≈ 448.

**Other quantities, all computed rather than asserted:**

* **Global traffic**, fold stage, XYZ, N=204: v4 765.0 KB/candidate → v5
  669.8 KB. v5 **removes** 95.2 KB (12.4 %) by not re-reading `c0`.
* **Traffic is irrelevant either way.** At v4-banded's measured 14.6 µs per
  candidate that is 47 GB/s — 3.0 % of A100 HBM. Even if v5 ran 3× faster it
  would be 9 %. The spec's "global reads not coalesced" risk and the
  bandwidth worry are both second-order by two orders of magnitude.
* **Producer-stage block-sequential steps**: v4 `3·N_sparse_t` (612 at N=204,
  1 530 at N=510) → v5 **1** staging pass.
* **Register ceiling**: 5 blocks/SM needs ≤ 96 registers/thread (65 536 regs ÷
  640 threads = 102, rounded down by allocation granularity). This is the one
  way the 5 is not reached, which is why the wrap reports CUDA's own number.

**The single number that decides what matters.** v4-banded measures **flat in
`T_obs`** while `N_sparse_t` grows with `T_obs`. The `O(N_sparse_t)` work — the
producer loop and both folds — is therefore *not* where the kernel spends its
time; the fixed-size node stage (two `get_tdi_raw` sweeps plus the log-polar
fits) is. That is model-free evidence that:

* v5's arithmetic and traffic savings are worth ~nothing;
* v5's **occupancy** change is worth everything — 1 → 5 resident blocks is five
  candidates in flight per SM to hide the node stage's dependent-FP and
  spline-lookup latency instead of one;
* and two optimisations I costed and then **rejected** are not worth their risk:
  replacing the six `THREAD_ZERO` amp-max scans with block reductions (~576
  sequential steps, ≲0.3 % of a candidate) and reordering the XYZ `h_h` loop to
  reconstruct 12 240 instead of 18 360 times (would also forfeit bit-identity).

It also bounds the downside. v5 adds no global traffic, needs no extra shared
memory, changes no arithmetic, and forfeits no L1 (unlike the global-slab
design, which needed carve-out 100 and left 28 KB of L1). The realistic worst
case is "the node stage was issue-bound, not latency-bound, and nothing moved" —
which is exactly the finding the experiment exists to produce.

## 4. What was validated, and how

### 4.1 The fold algebra — PASS, bit-identical

`scripts/gb_chunked_het/gb_sighet_v5_fold_model.py` (new; replaces the
now-deleted `gb_sighet_v5_producer_equiv.cxx`, which tested the superseded
three-pass producer). It models exactly the region v5 changes — the row floor,
the mask, the centred difference and both fold branches — with v4's
materialised producer in one arm and v5's mask + reconstruction in the other,
both running the same thread-strided accumulation the kernel uses.

Swept `nch ∈ {1,3}` × `m_half ∈ {0,2,4}` × `N_sparse_t ∈ {2,3,8,65,127,204}` ×
`stride ∈ {1,7}` × `tdi_type ∈ {0,1}` × `project_real ∈ {0,1}`, on `c0`
spanning 14 decades with 5 % exact zeros and a forced all-zero row, so the
`FLOOR_EPS` mask, the `1e-300` guard, the `N==2`, `N>=3`, `b==0` and `b==N-1`
branches all fire.

```
288 cases, 0 mismatches -> BIT-IDENTICAL
GATE: PASS
```

This is a build-free gate: it is the first thing to run after touching the
reconstruction, and it localises a failure when the compiled gate goes red.

### 4.2 Compiled kernels, CPU backend — PASS, exactly bit-identical

GBGPU rebuilt from this tree (`GBGPU_WITH_SHAREDMEM=OFF`, fresh
`cgbgpu.cpython-312-darwin.so`, `gb_signal_het_v5_get_ll` present), then
`gb_sighet_v5_parity.py` over 2 references × 10 candidates:

```
[worst] v5-flat vs v4-band : 0.000e+00
[worst] v5      vs v4-band : 0.000e+00
[worst] v5      vs v5-flat : 0.000e+00
[bit  ] exactly equal to v4 : 20/20 candidates
GATE: PASS
```

Not "within 1e-12" — **identical doubles**, which is what the design claims and
the strongest statement available without a GPU. It covers the mask precompute,
the `r`/`dr` reconstruction, both carve layouts and the `c0_mask_all` binding.

The parity script calls the binding directly, so the production dispatch was
checked separately (same scaffold, `N_sparse_t = 486`, 10 candidates through
`GBSignalHetComputations.get_ll`):

```
c0 (1, 3, 102, 486) complex128 | mask (1, 3, 102, 8) uint64
mask round-trips to the |c0| test: True
mask bytes / c0 bytes: 0.00823
  v5=1 vs v5=0 : max|diff| = 0.0 | bit-identical: True
  v5=2 vs v5=0 : max|diff| = 0.0 | bit-identical: True
GUARD: ok -> "sig-het v5 needs the |c0| row-floor mask ..."
```

i.e. the packed mask unpacks back to exactly `|c0| > max(1e-12·max_b|c0|,
1e-300)` element for element, costs 0.8 % of `c0`, and the `get_ll` branch plus
its no-active-reference guard behave.

Worth noting what the scaffold printed on the way:

```
[shmem] device limit 160 KB | N_sparse_t=486: v4-pcr 307 KB, v4-band 289 KB
```

At this grid v4-banded is **2.7× over the GPU per-block limit** — unrunnable,
not slow. v5 at N=486 is ~30 KB (4 blocks/SM). The CPU path has no such limit,
which is exactly why this asymmetry has been invisible until now.

### 4.3 CPU C++ compile — PASS

The `.cu` compiles clean as the CPU translation unit (the real build's
`.cu → .cxx` path), 0 errors.

### 4.4 Shared-budget sizer, C++ vs Python mirror — PASS

The benchmark's `sighet_v5_shared_bytes` must mirror the C++ exactly or the
`fit_nt_layer` grid solver sizes the wrong grid. Cross-checked by extracting the
C++ helpers verbatim into a standalone TU and comparing against the Python
mirror over **9 shapes × 2 modes**, including `n_knots=256`, `n_nodes=32`,
`m_half=7`, `nch=1` and `band_len=0`: **18/18 identical**.

That sweep caught a real bug. The aliased layout placed B/C/Bk/D at
`szA + szE`, assuming F (which overlays E) is the smaller of the two. It is at
the production shape (6 144 vs 9 536 B) but `n_knots > 2·n_nodes` flips it, and
F would then run off the end of E into B/C/Bk/D **while they are still live** —
silent corruption. Fixed to `szA + max(szE, szF)` in the sizer, the device carve
and the Python mirror.

### 4.5 Not validated

* ~~Any CUDA-specific compile error~~ — **CLOSED 2026-08-04: v5 compiles under
  `nvcc` on the GPU box.** This was the single largest unknown a laptop could
  not retire. Everything still open below is a runtime question, not a build
  one.
* Every performance and occupancy claim. Shared-vs-registers, residency and
  latency hiding are GPU-only.
* **The aliasing's dependence on `__syncthreads()`.** On CPU the arena is a
  plain host buffer and `NUM_THREADS_HERE == 1`, so every phase boundary is
  trivially satisfied. If a barrier is missing, only the GPU will say so — and
  the symptom would be mode 1 disagreeing with mode 2. That is exactly what the
  1-vs-2 arm of the parity gate is for.

## 5. GPU checklist for tomorrow

Ordered. Stop at the first failure.

**0. Rebuild GBGPU.** A stale `.so` silently hides new kernels; the parity
script probes for `gb_signal_het_v5_get_ll` and raises with that instruction.
The sig-het path does not need `GBGPU_WITH_SHAREDMEM=ON`:
```sh
export PIP_CONSTRAINT=<abs>/LISAanalysistools/constraints/sprint.txt
pip install -e . --config-settings=cmake.define.GBGPU_WITH_SHAREDMEM=OFF
```
Watch for a CUDA compile error in the V5 block — the one thing this laptop
could not rule out.

**1. Build-free algebra gate** (seconds, no GPU):
```sh
~/miniconda3/envs/deving/bin/python \
  LISAanalysistools/scripts/gb_chunked_het/gb_sighet_v5_fold_model.py
```
Expect `288 cases, 0 mismatches`.

**2. CPU correctness gate** (already green in this tree — rerun after the
rebuild to confirm the wheel):
```sh
BACKEND=cpu V4_REF_SEL=0,2 ~/miniconda3/envs/deving/bin/python \
  LISAanalysistools/scripts/gb_chunked_het/gb_sighet_v5_parity.py
```
Expect `GATE: PASS` **and** `exactly equal to v4 : N/N candidates`. Anything
non-zero means the reconstruction differs from what v4 materialised — chase it
even though the tolerance passes.

**3. GPU correctness gate:**
```sh
BACKEND=cuda12x V4_REF_SEL=0,2 GB_SIGHET_V5_VERBOSE=1 \
  ~/miniconda3/envs/deving/bin/python .../gb_sighet_v5_parity.py
```
Still expect bit-identity. Read the `[sighet v5]` line: it prints
**registers/thread** and CUDA's own **blocks/SM**. That line alone answers the
occupancy criterion. Expect `blocks/SM=5` at `N_sparse_t=204`.

If mode 1 and mode 2 disagree while mode 2 matches v4, the phase-lifetime
aliasing is the bug — a missing barrier between P2 and P3, or an array live
past the phase the table claims.

**4. If blocks/SM < 5, diagnose before benchmarking.** Almost certainly
registers (§3). This needs **no GPU** — the register count is a property of the
compiled cubin, so it can be read off a built wheel while waiting for hardware:

```sh
cuobjdump -res-usage $(python -c "import gbgpu_backend_cuda12x as m; print(m.__path__[0])")/cgbgpu*.so \
  | grep -B2 -A6 v5_get_ll
```

≤ 96 registers/thread means the shared-limited 5 blocks/SM is reachable; above
that, registers bind and the achievable number follows the table in §3.
`nvcc -Xptxas -v` on a rebuild gives the same figure. Report the number either way:
"4 blocks/SM because of registers" is a perfectly good result and it is what
tells us whether `__launch_bounds__(128, 5)` is worth trying — deliberately not
applied, because v4 has none and adding one only to v5 would confound the A/B.

**5. The measurement — matched grid, three arms.** At `N_sparse_t = 204`, one
build, same references:
```sh
USE_GPU=1 GPU_BACKEND=cuda12x \
BENCH_ENGINES="chunked,v4-band,v5-ctl,v5" BENCH_NTL=<the 204 value> \
  ~/miniconda3/envs/deving/bin/python \
  LISAanalysistools/scripts/gb_chunked_het/gb_engine_benchmark.py
```
Read three ratios, not one:
* `v5-ctl / v4-band` → everything that is **not** occupancy (the eliminated
  producer loop, the removed `c0` read). Expect ~1: §3 predicts this is noise.
* `v5 / v5-ctl` → **occupancy alone**, 5 blocks/SM against 3. This is the
  spec's actual question and the number that generalises.
* `v5 / v4-band` → the headline, and the number to quote.

Batch ladder to saturation as usual; below batch 64 the measurement is
launch-bound and meaningless.

**6. Accuracy sanity.** `timed_and_scored` gives one scored call per engine. v5
and v5-ctl must land on v4-banded's accuracy to the printed digits — a
correctness check, not a result.

**7. Only if 1–6 are green — the follow-on the spec scoped out.** v5's
footprint is constant, so `N_sparse_t` is no longer capped by shared memory.
Run `BENCH_ENGINES="chunked,v5"` with `BENCH_NTL` pushed to `N_sparse_t ≈ 510`
(still 4 blocks/SM) and see whether the **broad** accuracy degradation with
baseline — median 0.072 at 2 yr, 0.42 at 4 yr, still open in
`project_sighet_v4_plan` — improves. The catastrophic tail will not; that is
settled as node placement. The bulk has never been tested on GPU at a fine grid
because v4 physically could not run one. Note `gb_signal_het_make_reference`
has its **own** shared ceiling (`(Nt + n_sparse_fd + nt_layer)·16`, ~145 KB of
163 at Nt=8640) which v5 does not touch.
